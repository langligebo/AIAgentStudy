# Session 03：Prompt 设计与输出校验

[学习计划](../../LEARNING_PLAN.md) · [第一周笔记](../week1-llm-agent-basics.md) · [上一节](../session_02/README.md)

本节使用“客服消息分类”练习三个问题：如何把任务说清楚、如何公平比较 Prompt、如何判断模型是否完成任务。代码和学习材料已准备，不代表真实模型实验已经通过。

## 1. 先明确任务和输出

输入是客户的一句话，输出包含类别与是否需要澄清。以下是本课程的教学规则，不是所有客服业务的统一标准：

| 类别 | 判断规则 |
| --- | --- |
| 投诉 | 明确表达不满、质疑或要求追责；混合意图时优先归入投诉 |
| 售后 | 已有购买行为，申请退换、维修等处理，且未明确表达不满 |
| 咨询 | 询问商品、服务、规则等信息，且不属于上述情况 |
| 信息不足 | 无法判断意图，类别为 `null`，需要澄清 |

例如“我买的衣服想换一个尺码”，预期输出是：

```json
{"category": "售后", "needs_clarification": false}
```

“帮我处理一下”的信息不足，预期输出是：

```json
{"category": null, "needs_clarification": true}
```

`null` 是 JSON 的空值，Python 解析后是 `None`；`true` / `false` 对应 Python 的 `True` / `False`。带引号的 `"false"` 是字符串，不是布尔值。

## 2. Prompt 要把哪些内容说清楚

| 部分 | 本实验中的内容 |
| --- | --- |
| 角色 | 客服消息分类助手 |
| 任务 | 判断类别与是否需要澄清，不直接回答客户的问题 |
| 规则与约束 | 类别定义、混合意图优先级、信息不足的处理方式 |
| 输出格式 | 只返回指定字段的 JSON 对象，约定字段类型和取值 |

角色描述只是其中一部分。仅写“你是资深客服”没有定义分类边界、优先级或数据格式。

本节沿用 `common.llm` 的文本生成接口：这些指令、示例和待分类消息一起组成一个 prompt 字符串。`## 角色` 等标题只是文本组织方式，不等于 API 中真正的 `system` / `developer` 消息角色。消息角色与请求协议会在第 2 周学习。

## 3. 比较 A、B、C 三个版本

| 版本 | 变化 | 想观察的问题 |
| --- | --- | --- |
| A：普通描述 | 将全部规则写成一段连续文字，无输入输出示例 | 当前模型能否理解完整的自然段指令？ |
| B：分段描述 | 保留 A 的全部规则，按角色、任务、约束和格式分段 | 改变组织方式是否影响本批样本的表现？ |
| C：Few-shot | 在 B 的基础上增加 3 组输入与预期输出示例 | 示例是否帮助处理边界情况？ |

Few-shot 是把少量输入输出示例放入当前 Prompt，帮助模型理解模式；这一步不训练模型参数。可以参考 [OpenAI 官方 Prompt 指南](https://developers.openai.com/api/docs/guides/prompt-engineering#few-shot-learning)。本项目仍使用 Ollama，具体效果需要实验验证，不预设 C 优于 A 或 B。

公平比较的约定：

- 三个版本共用相同的规则常量，A 与 B 仅改变组织方式，C 增加示例。
- 每版运行相同的 6 条消息，共 18 次独立调用；按消息依次运行 A、B、C，不携带上一轮回答。
- 3 条 Few-shot 示例不在测试集中；测试预期答案只供 Python 评分，不传给模型。
- 模型、采样参数保持一致：`temperature=0`、`seed=42`、`top_p=0.9`、`top_k=40`、`max_tokens=512`。这些设置不保证跨环境完全可复现。
- 本节使用小型教学测试集。反复依据这些消息改 Prompt 后，它们就是开发样本，不能再当作独立的泛化证据；第 2 周会进一步划分开发集与保留测试集。

## 4. 程序分三层检查结果

```text
模型原始文本
  → JSON 能否直接解析？
  → 字段、类型、取值和字段之间的关系是否符合约定？
  → 分类与澄清决策是否符合该样本的预期答案？
```

对输入“帮我处理一下”，下面三种输出的问题不同：

| 模型输出 | JSON 语法 | 字段契约 | 任务结果 |
| --- | --- | --- | --- |
| `这是咨询。` | 失败 | 未通过 | 未通过 |
| `{"category":"咨询","needs_clarification":"false"}` | 通过 | 失败：布尔值写成了字符串 | 未通过 |
| `{"category":"咨询","needs_clarification":false}` | 通过 | 通过 | 错误：信息不足，应澄清 |

正确答案是 `{"category":null,"needs_clarification":true}`。是否澄清也是任务的一部分，不能只检查类别。

校验入口为 [main.py](main.py) 中的 `check_output()`。它直接解析原始回答，不剥离 Markdown 围栏，不补括号，也不先让模型修复答案。前后合法空白和字段顺序不影响判定。

目前采用基本 Python 检查：顶层对象、恰好两个字段、类别枚举、布尔类型，以及 `null` 与澄清标记的一致关系。第 2 周再学习 JSON Schema 和 Pydantic。

## 5. 阅读与运行顺序

三个文件各自负责一件事：

- [cases.py](cases.py)：示例与测试输入，以及预先确定的答案。
- [prompts.py](prompts.py)：公共规则与 A / B / C 三版 Prompt 的构造。
- [main.py](main.py)：调用共享客户端、三层校验、打印原始回答与统计。

先在项目根目录预览同一条消息的三版 Prompt，不请求模型：

```bash
uv run python -m week_01.session_03.main --preview --case T01
```

理解规则后，可以先用“混合意图”消息对比三版 Prompt，共 3 次真实请求：

```bash
uv run python -m week_01.session_03.main --case T05
```

完整实验，共 18 次真实请求：

```bash
uv run python -m week_01.session_03.main
```

需要只看一个版本时用 `--variant A`、`--variant B` 或 `--variant C`。`--model`、`--host`、`--timeout` 可临时覆盖根目录配置，调用统一经过 `common.llm.create_llm_client()`。脚本也支持按文件路径直接运行。

所有 Prompt 预览、回答、错误和统计仅打印到控制台，不创建结果文件。没有增加新依赖。

## 6. 怎样读统计结果

完整实验中，每个版本的三个通过率都以 **6 条测试消息** 为分母。比如 6 条里只有 4 条解析成功，这 4 条又全部分类正确，任务正确率仍是 `4/6`，不是 `4/4`。

语法错误、字段错误或分类错误会保留在控制台并继续测试后续样本。连接失败等调用错误会停止整轮实验，不自动重试；手动中断也会停止。未完成时只展示计数与覆盖情况，不显示百分比，也不能据此比较版本优劣。

如果响应结束原因为 `length`，程序不将它计为任务成功，即使截断前碰巧形成合法 JSON；应提高 `GENERATION_OPTIONS` 中的 `max_tokens` 后重新运行完整比较。

实验正常跑完时退出码为 0，即使存在分类失败；调用错误为 1，手动中断为 130。程序正常结束与模型全部答对是两个不同概念。

三版结果一样、Few-shot 版本更差，都是可能的真实观察。保留原始错误信息，分析是哪一层失败，不为了得到预期结论而筛掉失败样本。

## 7. 本节练习与验收

先回答：输入“帮我处理一下”，模型返回合法对象 `{"category":"咨询","needs_clarification":false}`，能直接认定分类成功吗？是哪一层出了问题？

之后查看三版 Prompt，运行实验并观察：哪些消息发生分类分歧？哪种版本更容易输出额外解释或错误字段？示例中的投诉优先级是否被用于未见过的混合意图消息？结论只限于实际观察到的样本。
