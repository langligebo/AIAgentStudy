## Session 1：模型调用与核心参数

### 1.1 先区分三个组成部分

| 组成部分 | 本项目中的例子 | 主要职责 |
|---|---|---|
| 模型 | `qwen2.5:14b` 对应的本地模型 | 根据输入生成输出；实际能力需要通过任务验证 |
| 推理服务 | Ollama | 加载模型、接收请求、执行推理并返回响应 |
| 客户端与应用 | Python 实验脚本，后续的 Agent 程序 | 构造请求、管理消息与状态、校验结果、执行工具、记录实验 |

模型支持某项能力、服务提供相应接口、客户端正确使用接口，是不同层面的条件。仅有能聊天的模型，或在磁盘上放入一个 `SKILL.md`，都不会自动形成完整的 Agent。

### 1.2 训练、推理、微调、RAG 与 Skills 的边界

| 概念 | 本阶段需要理解的区别 | 后续安排 |
|---|---|---|
| 训练 | 使用数据优化模型参数 | 先理解原理，深入训练作为选修 |
| 推理 | 使用已有模型参数处理当前输入、生成结果 | 本周开始实际调用 |
| 微调 | 在已有模型基础上继续训练，改变参数以适配任务 | 主线后选修，先建立评估基线 |
| RAG | 检索相关资料并放入当前请求的上下文，通常不修改模型参数 | 第 6 周实现 |
| Skills | 将任务方法、步骤及配套资源组织为可按需加载的技能 | 第 5 周实现发现、选择和加载 |

本周只需要解释它们分别解决什么问题，不实现检索系统、技能加载器或微调流程。

### 1.3 Token 与 Context Window

- **Token** 是模型处理文本时使用的单位，不等于字符或单词；同一段中文或英文的 token 数取决于模型使用的分词器。
- **Context Window**（上下文窗口）限制一次推理能够处理的上下文规模。系统指令、用户输入、历史消息、工具结果和生成内容都会影响上下文预算，具体限制需结合模型及服务配置确认。
- 多轮工具调用和长对话容易用尽预算，需要决定保留哪些信息。第 7 周进一步学习上下文与记忆管理。

### 1.4 Temperature（温度）

- 在采样生成中调整候选 token 的概率分布；可用范围和具体行为以推理服务实现为准。
- **temperature = 0** 通常用于降低随机性，适合作为稳定性实验的基线；不保证答案正确，也不保证跨版本、硬件和运行条件逐字一致。
- **temperature = 0.5 / 1.0** 可以用于观察采样差异；更高的多样性是否有用，需要同时检查任务质量和约束遵守情况。
- 工具选择需要通过评估确定合适设置，不能只依赖低温保证正确性。

### 1.5 Top_p（核采样）

- 根据候选 token 概率的累计阈值选择采样集合。
- 与 temperature 都会影响采样。初学实验应尽量一次改变一个变量，才能解释观察到的差异。

### 动手实验

使用现有的 [Temperature 实验脚本及说明](session_01/README.md)，让 Ollama 的 `qwen2.5:14b` 对同一 prompt，在 `temperature = 0 / 0.5 / 1.0` 下各运行 3 次。

实验要求：

1. 保持 prompt 和其他参数一致。现有脚本固定 `top_p = 0.9`、`top_k = 40`、`max_tokens = 512`（调用模块将其转为 Ollama 的 `num_predict`）；三组分别使用相同的种子序列 `42、43、44`，同一序号配对比较。
2. 检查文本一致性和表达差异，同时人工判断是否完成任务、是否满足输出约束。
3. 记录模型标识、可获得的模型版本或摘要、Ollama 版本、硬件、参数、耗时和截断情况，方便解释差异。脚本未自动收集的环境信息手动补充。
4. 每组 3 次是小样本观察，不能据此证明某种温度在所有任务上更好。没有差异也应如实记录。

现有脚本只对比 **temperature**，没有进行 Top_p 扫描。Top_p 对比作为可选扩展：固定 temperature，在新的完整实验中只改变 `top_p`，独立记录结果。

### 初步模型能力记录

建立一份能力记录，区分“待验证”“通过当前样本”“当前样本失败”和“当前组合无法测试”，不要把未测试的能力写成已支持。

| 能力 | 本周检查方式 | 需要记录的证据 |
|---|---|---|
| 基础指令遵守 | Temperature 实验中检查数量、内容和长度等约束 | 输入、原始输出、人工判断依据 |
| JSON 与分类任务 | 在 Session 3 用相同测试输入检查 | 语法通过率、字段校验通过率、分类正确率 |
| 耗时与输出截断 | 查看控制台输出并观察本机运行情况 | 每次耗时、结束原因；资源占用可手动补充 |
| 结构化输出接口 | 本周仅列为待验证 | 第 2 周检查服务接口和模型表现 |
| 工具调用与多步执行 | 本周仅列为待验证 | 第 3～4 周检查调用结构、工具结果回传和任务完成情况 |

## Session 2：单次调用、Workflow 与 Agent

### 2.1 先辨认执行方式

| 执行方式 | 谁决定下一步 | 客服场景例子 |
|---|---|---|
| 单次 LLM 调用 | 应用提交一次输入并消费结果 | 将一条消息分类为咨询、投诉或售后 |
| 固定 Workflow（工作流） | 代码预先定义步骤和分支；步骤中可以包含模型调用 | 分类 → 按类别查询固定资料 → 生成答复 |
| Agent | 模型在程序允许的范围内，根据任务状态和工具结果选择下一步 | 发现订单信息不足后追问，查询订单与政策，根据返回结果决定是否需要进一步查询或结束 |

简单客服分类属于单次模型调用，也可以作为工作流中的一个步骤；仅有分类功能不足以说明系统是 Agent。固定工作流同样可以包含循环、分支和工具调用，区别在于谁决定后续执行路径。

本课程采用一个便于实现的工作定义：**Agent = 模型决策 + 可执行工具或环境交互 + 状态与反馈循环 + 结束条件**。程序负责限制可用动作、检查权限和校验结果。

### 2.2 决策与反馈循环

```text
读取任务与当前状态
        ↓
模型选择下一步：回答 / 追问 / 调用工具 / 结束
        ↓
程序校验并执行允许的操作
        ↓
记录工具结果与任务状态 → 再次决策，直到完成或达到退出条件
```

任务开始时先写清楚目标、必要输入、约束和完成条件。信息不足时追问；无法完成时说明缺少的条件。最大步数、预算和取消机制会在后续实现中展开。

### 2.3 Reactive 与 Planning：辅助理解决策方式

| 方式 | 特点 | 例子 |
|---|---|---|
| **Reactive**（反应式） | 根据当前状态决定下一步，不一定维护显式的多步计划 | 根据上一轮查询结果决定继续查询还是回答 |
| **Planning**（规划式） | 生成或维护多步计划，并在执行结果变化时调整 | 先列出核对订单、查政策、拟处理方案等步骤，再逐步执行 |

这是一种辅助分类视角，不是所有 Agent 系统的唯一分类；同一系统可以同时包含两种方式。是否有显式计划，也不能代替对工具执行、结果反馈和任务完成情况的检查。

### 动手任务

选择现有客服系统，或用“查询订单状态”作为模拟案例，完成一份分析：

1. 写出目标、必要输入、可用工具、约束和完成条件。例如“拿到有效订单状态并告知用户”，而不是仅以“模型说查询成功”作为完成依据。
2. 分别画出单次调用、固定工作流、Agent 三种实现的步骤，标明每个分支由代码还是模型决定。
3. 对实际系统按已有证据分类；没有工具调用和反馈循环时，不标记为已经具备 Agent 能力。
4. 列出变成多步骤 Agent 需要补齐的能力，包括参数校验、追问、状态、结果验证、结束条件及失败处理。
5. 解释该任务是否值得增加自主决策，以及哪些步骤适合由固定代码完成。

## Session 3：Prompt 工程与输出校验

### 3.1 System Prompt 的结构化写法

一个结构清晰的 System Prompt 可以包含四部分：

1. **角色设定（Role）**：明确模型的职责和表达方式。
2. **任务描述（Task）**：具体要做什么，输入和完成标准是什么。
3. **约束条件（Constraints）**：必须遵守的规则，以及信息不足时如何处理。
4. **输出格式（Output Format）**：字段、类型、可选值和示例，方便程序消费结果。

Prompt 能帮助表达要求，但不能代替程序校验、权限检查或业务判断。后续会使用结构化输出接口及 Schema 校验进一步约束结果。

### 3.2 Few-shot 示例设计原则

- **从少量示例开始**：先用 2～3 个示例观察收益，再根据失败样本调整；不存在适合所有任务的固定数量。
- **覆盖边界情况**：除了正常输入，还要展示信息不足、混合意图等情况应如何处理。
- **保持字段与规则一致**：字段名、类型、可选值和业务规则需要与要求一致。合法 JSON 中无关紧要的空白通常不影响解析，不要求逐字匹配示例排版。
- **验证示例选择和顺序**：它们可能影响结果，应通过测试比较；不要将固定顺序当作普遍最优规则。
- **示例与测试分开**：用于 Prompt 的示例不计入测试准确率，避免把记住示例当成泛化能力。

### 3.3 三层正确性

| 层次 | Python 中如何检查 | 可能的失败 |
|---|---|---|
| JSON 语法 | `json.loads()` | 返回 Markdown 代码围栏、解释文字或不完整 JSON，导致直接解析失败 |
| Schema / 字段约束 | 本周可用类型和枚举检查，第 2 周系统学习 Schema 与校验库 | 可以解析，但缺字段、类型错误或出现未定义类别 |
| 业务正确性 | 对照预先标注的答案与规则 | 字段合法，但分类不对，或信息不足时仍然强行猜测 |

“可以解析”不等于“字段正确”，字段正确也不等于任务完成。应分别统计每一层的结果。

### 动手任务

编写客服意图分类 Prompt，比较三个版本：

1. **版本 A**：用自然段描述任务和规则，不分段组织，无示例。
2. **版本 B**：保留相同任务、规则和输出要求，按角色、任务、约束、格式组织，无示例。
3. **版本 C**：在版本 B 基础上加入 2～3 个 few-shot 示例，包含至少一个边界情况。

三个版本使用同一套规则和测试数据，避免把规则差异误认为结构化写法的效果。示例分类规则：

- **投诉**：明确表达不满、质疑或要求追责，存在混合意图时优先归入投诉。
- **售后**：已有购买行为，申请退换、维修等处理，且未明确表达不满。
- **咨询**：询问商品、服务、规则等信息，且不属于上述情况。
- **信息不足**：例如“帮我处理一下”，返回空类别并请求澄清。

采用统一输出：

```json
{"category": "售后", "needs_clarification": false}
```

信息不足时：

```json
{"category": null, "needs_clarification": true}
```

准备 5～8 句未放入 few-shot 示例的测试输入，提前写好预期答案；固定模型、采样参数和种子策略，对每个版本运行同一批输入。

使用 Python 的 `json.loads()` 解析原始结果，再检查它是对象、字段集合正确、`category` 为三个允许类别之一或 `null`、`needs_clarification` 为布尔值，且空类别与需要澄清相对应。最后比对分类和澄清决策是否符合预设答案。

报告同时列出：直接 JSON 解析通过率、字段校验通过率、任务正确率，以及失败样例。以所有测试用例为分母计算整体任务正确率，将解析失败和字段错误计为未完成，避免仅对成功解析的子集计算出过高准确率。需要清洗才能解析的结果可以另行记录，但不算直接解析成功。

## 补充讨论：模型能力提升后，Prompt 还需要写得复杂吗？

Prompt 的目标是把任务说清楚，长度和复杂度本身不是质量标准。明确目标、规则和输出契约后，应该通过实验判断是否还需要增加示例或细化指令。

- 有工具反馈和多轮修正的应用，可以根据测试结果、查询结果和用户反馈继续调整。
- 单次分类或结构化输出经常由下游程序立即消费，因此需要清楚的字段约定及校验机制。
- 多步 Agent 即使能继续尝试，也需要限制次数、检查业务结果，避免重复执行或错误持续传播。

无论结果由人还是程序消费，都要验证任务是否完成；由程序消费时，还要明确数据契约。Prompt 是系统可靠性的一部分，校验、工具设计、权限和评估同样需要实现。

**1.（单选）** 在需要观察工具选择稳定性的实验中，通常适合先从哪种 temperature 设置建立基线？

- A. 接近 1.0，保证任务正确
- B. 接近 0，降低采样随机性，再验证正确率和一致性
- C. 无所谓，工具选择不受生成行为影响
- D. 设置为负数以获得更确定的结果

<details><summary>参考答案</summary>

B。低温通常有助于降低采样随机性，但不能保证选择正确或在所有环境中逐字一致。工具和参数仍需程序校验，并通过实际样本评估。

</details>

**2.（单选）** 一个系统仅用一次模型调用把客服消息分为三个类别，没有后续工具执行和反馈循环，应首先归为：

- A. 单次 LLM 调用
- B. 已完整实现的 Planning Agent
- C. 多 Agent 协作系统
- D. 只要使用模型就一定属于 Agent

<details><summary>参考答案</summary>

A。分类可以成为工作流或 Agent 的组成步骤，但单独的分类能力不足以证明存在自主决策和环境反馈循环。Reactive 与 Planning 是进一步讨论决策方式时的辅助视角。

</details>

**3.（简答）** 为什么模型输出通过 `json.loads()`，仍不能认定任务成功？

<details><summary>参考答案要点</summary>

`json.loads()` 只验证 JSON 语法并解析为 Python 对象；解析结果可能不是预期的对象，也可能缺少字段、字段类型错误或类别不合法。即使字段全部合法，分类仍可能错误。在工具调用场景中，还需要验证工具名称、参数、权限和实际执行结果。程序应分别检查语法、Schema / 字段约束、业务条件。

</details>

---

**4.（简答）** 为什么 Few-shot 示例要覆盖边界情况，并与测试集分开？合法 JSON 的空白差异是否应算失败？

<details><summary>参考答案要点</summary>

边界示例能展示信息不足和混合意图时应如何处理，减少无依据猜测。测试数据与示例分开，才能观察模型能否处理没有直接展示过的输入。JSON 语法允许的无关空白不应作为失败依据；字段名、类型、值域和业务规则才是需要检查的契约。

</details>

---

**5.（判断题）** “模型能力强了，只要输出看起来合理，就不需要明确 Prompt 规则或验证任务结果。”这个说法对吗？

<details><summary>参考答案要点</summary>

不对。清楚的目标和规则有助于模型完成任务，但 Prompt 本身也不保证成功。应根据任务验证数据格式、工具执行和实际业务结果，并通过实验决定 Prompt 需要多详细。复杂或冗长不等于可靠。

</details>

**7.（简答）** 在 Ollama + Python 项目中，模型、推理服务和客户端分别做什么？把一个 `SKILL.md` 放进目录后，模型会自动使用它吗？

<details><summary>参考答案要点</summary>

</details>
