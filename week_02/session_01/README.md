# Session 01：模型能力验证与请求协议

[第二周入口](../README.md) · [完整学习计划](../../LEARNING_PLAN.md) · [上一节](../../week_01/session_03/README.md)

上一节比较了 Prompt 的写法。这一节进一步检查：请求中怎样区分消息角色，模型如何获得历史信息，接口怎样返回 JSON、文本片段或工具请求。

本节是能力预检。已有代码与离线测试不代表远程模型已通过；运行后结合原始响应判断当前组合的表现。

## 1. 区分模型、服务与客户端

| 层次 | 本项目中的例子 | 要确认的事情 |
| --- | --- | --- |
| 模型 | 配置中的 `qwen2.5:14b` | 能否理解当前输入、遵守约束、选择正确动作 |
| 推理服务 | 局域网 Ollama | 当前版本是否接受所需参数、怎样组织响应 |
| 客户端 | `common/llm.py` | 请求是否正确，能否解析响应、识别结束和错误 |

只有三层一起工作，应用才具备可用能力。收到 HTTP 错误、模型返回错误答案、客户端错误地处理响应，需要分别分析；不能只根据模型名字认定功能可用。

## 2. 从一段 Prompt 到带角色的消息

第一周用 `client.generate(prompt)` 提交文本。本节新增 `client.chat(messages)`，在当前 Ollama 适配器中对应 `/api/chat`，历史作为消息数组显式传入。[Ollama Chat 接口](https://docs.ollama.com/api/chat)

```python
from common.llm import create_llm_client

client = create_llm_client()
messages = [
    {"role": "system", "content": "你是客服消息分类助手，只输出类别。"},
    {"role": "user", "content": "这款键盘支持蓝牙吗？"},
]
response = client.chat(messages)
print(response.text)
```

| 角色 | 本课程中的用途 |
| --- | --- |
| `system` | 应用设定的任务和行为要求 |
| `user` | 用户当前请求或此前的用户消息 |
| `assistant` | 模型此前返回的内容或工具调用请求 |
| `tool` | 程序执行工具后提供的结果，第 3 周进一步使用 |

消息角色和文本里的标题不同：写下“## 系统指令”不会自动成为 API 的 `system` 消息。角色也不能代替程序中的参数与权限检查。

## 3. 多轮对话的历史由程序提供

本节做一个对照：先告诉模型一个模拟订单号，再问“我刚才提供的订单号是什么”。

```text
带历史：system + user（订单号）+ assistant（真实首轮回复）+ user（追问）
不带历史：system + user（追问）
```

代码会将首轮真实回答放回第二轮消息。对照请求则不传订单号，期望模型回答“未提供”。检查重点是当前请求到底带了什么信息，而不是模型是否“认识这个用户”。

`common.llm` 不在客户端内部保存会话；本实验中的历史仅存在于运行进程中。第 7 周会进一步区分对话上下文、任务状态与长期记忆。

## 4. 在 Prompt 中要求 JSON，与接口约束 JSON

上一节依靠 Prompt 要求模型返回 JSON。本节同时向接口传递一个小型 JSON Schema，约定输出的字段、类型和允许值。Ollama 用请求中的 `format` 接收该 Schema；本项目对外命名为 `response_schema`。[结构化输出说明](https://docs.ollama.com/capabilities/structured-outputs)

实验输入：“请查一下订单 QX-731。”本节只提取信息，没有执行查询，所以期望：

```json
{"order_id": "QX-731", "status": "待查询"}
```

Schema 可以限制字段结构，但订单号是否提取正确仍要检查。程序会将完整对象与预期答案比较；本节只认识接口用法，下节再系统学习 JSON Schema 与 Pydantic。

## 5. 流式响应：可以先展示，必须等完整结束后再验收

非流式调用等待完整响应。流式调用按顺序返回片段，客户端可以边接收边显示。Ollama 的 HTTP 流式响应使用 NDJSON，即一行一个 JSON 事件，不是把整个响应体当作一个 JSON 对象解析。[流式协议说明](https://docs.ollama.com/api/streaming)

```text
接收一行事件 → 解析事件 → 取出文本片段 → 累积并显示
                                                ↓
                                  收到 done=true 才组装完整结果
                                                ↓
                                    校验完整 JSON 与业务结果
```

这里有两层数据：每一行是接口事件 JSON，其中的 `message.content` 才是模型输出的文本。单个文本片段可能只是半个 JSON 字段，不能直接当完整业务对象校验。

本项目的使用方式是：

```python
response = client.chat(
    messages,
    on_text=lambda piece: print(piece, end="", flush=True),
)
# chat() 正常返回后，response.text 才是已收到结束标记的完整文本。
```

`messages` 使用前面示例中的消息列表即可。实验代码还会对同一任务比较非流式和流式的最终 JSON 数据，不要求空白、字段顺序或分块位置一致。

如果连接在 `done=true` 前结束，即使控制台已经显示了一段看起来完整的文字，客户端也会报错。`done=true` 只表示本次生成结束；是否因长度限制截断、是否答对，还要分别检查。

当前客户端只支持文本流式处理，工具探针使用非流式。流式工具调用的增量组装不在本节实现范围内。

## 6. 工具调用的最小探针

工具定义告诉模型：可以提出什么动作，需要哪些参数。Ollama 将结构化的调用请求放在响应的 `message.tool_calls` 中。[工具调用说明](https://docs.ollama.com/capabilities/tool-calling)

本节声明一个教学工具 `get_order`，要求模型为模拟订单 `QX-731` 提出调用请求。公共模块将返回值整理为：

```text
ToolCall(name="get_order", arguments={"order_id": "QX-731"})
```

通过条件：恰好一个调用、工具名正确、参数恰好为指定订单号，并且响应完整且未截断。

本节没有实现或执行 `get_order`。模型普通文本中写“已查询”或“调用 get_order”都不能代替协议中的工具请求。返回正确调用结构，也不代表已经验证工具执行、权限校验或执行结果回传；这些在第 3 周实现。

如果当前服务明确返回不支持工具的错误，保留控制台原始信息，说明当前组合不能完成该探针。一次没有产生工具请求，只能说明本样本未通过，不能推断所有工具场景都不支持。

## 7. 区分上下文容量和输出预算

| 本项目参数 | Ollama 参数 | 本节用途 |
| --- | --- | --- |
| `context_tokens` | `num_ctx` | 请求使用的上下文窗口大小，本节设为 4096 |
| `max_tokens` | `num_predict` | 本次生成的输出 token 上限，通常设为 256 |

这两个参数含义不同；参数映射参考 [Ollama 参数说明](https://docs.ollama.com/modelfile#valid-parameters-and-values)。输入中的指令、历史、工具定义以及输出都会占用上下文相关预算，不能把输出上限当作模型的整个上下文容量。

“请求 4096”不是“证明模型最大支持 4096”。实际运行还受模型、服务配置与资源约束；本节使用短输入，不进行上下文容量极限测试。更大的上下文设置也会增加运行所需内存。[上下文说明](https://docs.ollama.com/context-length)

截断实验要求模型列出 1～50，却将 `max_tokens` 临时设为 1，观察是否出现 `finish_reason=length`。此时“观察到截断”是实验目标达成，“成功列出所有数字”则没有达成。客户端会保留结束原因，而不是把这种响应当作完整的业务答案。

## 8. 实验清单与运行顺序

在项目根目录执行，所有结果只打印到控制台。

先查看清单，不连接模型：

```bash
uv run python -m week_02.session_01.main --list
```

| `--probe` 值 | 实验 | 正常完成时的请求数 |
| --- | --- | --- |
| `instruction` | 中文指令与消息角色 | 1 |
| `structured` | 接口级结构化输出 | 1 |
| `history` | 首轮、带历史追问、不带历史追问 | 3 |
| `stream` | 同一任务的非流式与流式请求 | 2 |

```bash

```

完整运行六项实验，正常共 9 次请求：

```bash
uv run python -m week_02.session_01.main
```

各项可以单独运行，例如 `--probe stream`。地址、模型和超时继续读取根目录 `config.toml`；`--host`、`--model`、`--timeout` 可临时覆盖。无需安装新依赖，也支持按文件路径运行脚本。

## 9. 怎样解释结果

| 状态 | 含义 |
| --- | --- |
| 通过当前样本 | 本次响应满足该探针的条件，不等于所有同类任务都可靠 |
| 当前样本未通过 | 收到响应，但文本、参数、结束原因等没有达到预期 |
| 调用或协议失败 | 接口拒绝、响应结构错误等导致未能完成验证；查看具体错误 |
| 连接失败或超时 | 停止后续请求，不重复触发同一连接问题 |
| 未运行 / 用户中断 | 尚无完整证据，不标记为模型能力失败 |

模型回答未通过时仍继续其他探针。单项 HTTP 或协议错误也继续其他独立探针；连接失败或超时则停止整轮。不会自动重试。首段文本延迟只是客户端观察值，不能单次据此断言流式推理总耗时更短。

退出码 0 表示实验流程正常跑完，不保证每项模型回答都通过；调用失败为 1，用户中断为 130。原始请求、回答、结束原因及已知 token 计数都在控制台展示，不生成报告文件。
