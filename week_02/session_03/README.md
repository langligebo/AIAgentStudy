# Session 03：调用失败处理、能力基线与测试样本划分

[第二周入口](../README.md) · [完整学习计划](../../LEARNING_PLAN.md) · [学习进度](../../LEARNING_PROGRESS.md) · [上一节](../session_02/README.md)

## 1. 本节目标与学习顺序

上一节解决“收到回答后怎样校验”。这节向前后各延伸一步：没有拿到可用回答时怎样定位；拿到一批结果后怎样判断当前系统的表现。

仍使用知识库客服助手的意图分类任务，沿用咨询、投诉、售后和信息不足的规则。前置知识是消息角色、响应结束原因，以及 JSON 语法、字段契约和任务判断三层校验。

本节按四步学习，预计 60～90 分钟：

1. 区分调用失败、响应不完整和任务判断错误。
2. 用离线故障注入检查程序分支，不依赖真实服务恰好出错。
3. 建立开发集和保留测试集，固定实验条件。
4. 阅读控制台能力基线，复盘第二周，并准备第三周工具调用。

验收目标是能解释失败属于哪一层、知道哪些结果尚未验证，并能用固定样本做一次可复查的分类实验。本节不自动重试，不执行工具，也不新增模型服务或依赖。

## 2. 程序正常返回，不等于业务成功

```text
请求发出
  ├─ 连接失败 / 超时 → 记录调用未完成，停止本轮后续请求
  ├─ 接口或响应协议错误 → 记录具体诊断
  └─ 客户端返回响应对象
       ├─ length / 未识别结束原因 / 意外工具请求 → 不判定成功
       └─ 正常结束
            ├─ 空文本 → 不判定成功
            └─ JSON 语法 → 字段契约 → 与预期答案比较
```

例如 HTTP 200、收到 `done=true`、得到合法 JSON，是不同层次的观察。Ollama 的 `done` 表示响应结束，`done_reason` 描述结束原因；它们不证明模型分类正确。[Ollama Chat 响应字段](https://docs.ollama.com/api/chat)

一个特别容易误判的例子：模型恰好输出了完整 JSON，但结束原因是 `length`。本课程仍将它标记为截断，不补括号、不忽略结束原因后算成功。先检查输出预算和任务要求，修正后再进行新的、明确记录的实验。

## 3. 失败分类与当前客户端的能力边界

| 情况 | 能确定什么 | 本节处理 |
| --- | --- | --- |
| 连接失败或超时 | 没有取得可验收的完整调用结果 | `connection_or_timeout`，停止整轮，不自动重试 |
| HTTP 拒绝、响应协议异常等 | 当前调用或客户端解析失败 | `call_error`，记录诊断；其他独立样本可继续 |
| 输出到达长度限制 | 生成被截断 | `truncated`，不继续业务评分 |
| 未识别结束原因 | 缺少可接受的正常结束证据 | `unknown_finish`，待调查 |
| 分类任务返回工具请求 | 响应不符合本任务契约 | `unexpected_tools`，不执行工具 |
| 正常结束但文本为空 | 没有可用分类输出 | 防御性检查为 `empty`；真实客户端可能更早报错 |
| JSON 无法解析 | 输出格式不符合约定 | `invalid_json` |
| 字段、类型或关系错误 | JSON 可解析，契约不合法 | `invalid_schema` |
| 分类或澄清判断错误 | 结构正确，任务没答对 | `wrong_answer` |
| 用户中断 | 本轮没有按计划完成 | `interrupted`，保留覆盖情况并退出 |

要区分“概念上想记录的分类”和“当前代码确实提供的信息”：

- [公共客户端](../../common/llm.py) 将连接、读超时等包装成 `LLMConnectionError`，本节不会靠匹配错误文本强行推断到底是哪一种网络原因。
- HTTP 错误、空回答、流在结束标记前断开等，当前可能表现为 `RuntimeError`。实验会归入 `call_error`，同时保留诊断文本；并未实现稳定的 HTTP 状态码字段或专用空回答异常。
- 离线实验可直接注入空 `LLMResponse`，检查评估器自身的防御分支。这不代表真实客户端一定会将空回答原样交给评估器。
- 流式响应可能在 HTTP 成功之后才出现错误事件。Ollama 文档说明，此时原 HTTP 状态码不会改变；因此不能只检查最初的 HTTP 状态。[Ollama 错误处理](https://docs.ollama.com/api/errors)

拒绝回答还要单独理解：普通文本“我不能回答”在本分类任务中会因不是约定 JSON 而失败，但这并不能自动证明它是安全拒绝、能力不足或 Prompt 歧义。当前统一 `LLMResponse` 没有专门的拒绝标志，不能虚构一个；应结合原始输入输出复核。信息不足时返回 `category=null` 是本课程要求的澄清结果，不是拒答。如果另一种业务要求拒绝越权请求，该拒绝可以是任务成功，需事先定义预期。

## 4. 实验一：离线注入故障

先在项目根目录运行：

```bash
uv run python -m week_02.session_03.main
```

默认模式是 `faults`，**不读取模型连接配置、不连接远程模型、不产生结果文件**。它使用本地构造的响应和异常，检查 12 个场景：成功、网络超时、调用错误、空回答、截断、未知结束原因、意外工具请求、JSON 错误、类型错误、分类错误、文本拒答和用户中断。

阅读 [main.py](main.py) 中的 `evaluate_call()`。它先调用传入的函数，再检查响应，最后复用第一周的 `check_output()` 做三层分类校验。这里复用已经落地的校验器，将新内容集中在可靠性；上一节教案中的 Pydantic 模型也可以替换字段校验部分。

最小用法：

```python
from common.llm import LLMResponse
from week_01.session_03.cases import Case
from week_02.session_03.main import evaluate_call

case = Case("example", "这次送错颜色让我很不满，我要求换货。", "投诉")
raw = '{"category":"投诉","needs_clarification":false}'
result = evaluate_call(lambda: LLMResponse(raw, "length"), case)
print(result.status)  # truncated：即使 JSON 和答案看起来正确，也不计为成功。
```

故障注入“通过”表示评估程序识别到了预设故障，不表示模型擅长分类。离线执行时间也不是模型延迟。尝试将结束原因改成 `stop`、类别改成售后、布尔值改成字符串，先预测结果，再运行验证。

## 5. 为什么本节不写一个无条件重试循环

在再次调用前，先回答三个问题：

1. 原因是临时问题，还是原样重试必然重复的错误？例如缺参数、模型名错误，应先修正请求。
2. 调用是否会产生外部写入？纯分类主要消耗时间或费用；后面的创建工单、发送消息则可能已经生效。
3. 是否有次数、总时间和成本上限？是否能记录第一次失败，而不是只留下最后一次成功？

本课程本节统一不自动重试。未来可对明确适用的临时失败增加有上限的退避；涉及写入且结果未知时，要先查状态或使用业务幂等机制，不能把超时理解为“肯定没有执行”。第三周与第八周会进一步落实这些边界。

另外，当前客户端的 socket 超时不应被当作整个 Agent 任务的全程预算。多次请求和流式读取的总耗时需要单独控制，本节没有实现任务级总截止时间。

## 6. 开发集与保留测试集

开发集帮助修改 Prompt、规则和代码；保留测试集用于在方案固定后验收。一个样本一旦被反复用来指导修改，就已经参与开发，不能继续当作未见过的独立证据。

本节的 [cases.py](cases.py) 提供教学起点：

| 集合 | 内容 | 用途 |
| --- | --- | --- |
| `dev` | 第一周已用过的 6 条客服消息 | 观察失败、改 Prompt、调试评分器 |
| `test` | 新准备的 8 条消息，四类各 2 条 | 方案固定后做一次保留验收 |

测试答案只由 Python 评分器读取，`build_messages()` 只接收待分类消息，不能把当前样本的预期答案拼进模型请求。不同集合的 ID 与文本应不重复，也要人工检查近似改写、同一订单或同一对话泄漏的问题。

这是一个很小的教学划分，不能支持泛化结论。样本在仓库里可以查看，并无权限隔离；保持“保留”的关键是不要根据测试集结果反复调整方案。若已经用其调参，就将它视为开发数据，准备新的保留样本。

保持评估数据独立的原则可参考 [scikit-learn 的数据泄漏说明](https://scikit-learn.org/stable/common_pitfalls.html#data-leakage)。本节将同一原则用于 Prompt 和方案选择，不训练模型参数，也不引入 scikit-learn 依赖。

## 7. 实验二：建立真实模型基线

这一节开始会真正调用模型。先运行开发集，默认 6 次请求：

```bash
uv run python -m week_02.session_03.main --mode baseline --split dev
```

脚本使用 `common.llm.create_llm_client()`，读取统一 `config.toml`；`--model`、`--host`、`--timeout` 可临时覆盖。所有请求使用独立消息，不把前一个样本的回答当作后一个样本的历史。

固定参数为 `temperature=0`、`seed=42`、`max_tokens=256`、`context_tokens=4096`，同时发送本分类任务的 JSON Schema。Schema 限制基本结构，字段关系和任务正确性仍由本地检查。固定 seed 不构成跨版本或硬件的确定性保证。

需要观察重复运行时可执行：

```bash
uv run python -m week_02.session_03.main --mode baseline --split dev --repeat 3
```

正常为 `6 × 3 = 18` 次请求。重复轮次不增加独立样本数量，仍然只有 6 条输入；不要把它写成 18 个不同测试样本。模型权重、量化、服务版本、硬件、Prompt、数据集及采样条件变化时，应分开记录和比较。

Prompt 与参数固定后，再单独运行保留测试集，默认 8 次请求：

```bash
uv run python -m week_02.session_03.main --mode baseline --split test
```

不要把保留集放进每次调 Prompt 都执行的循环。本次只验证了离线程序，未运行以上真实请求；当前模型在这些样本上的分数仍是未验证。

## 8. 怎样阅读控制台报告

脚本逐条打印输入、原始回答、结束原因、已知 token 计数、调用耗时、状态和诊断，最后打印计数汇总，不创建报告文件。

| 指标 | 本节含义 |
| --- | --- |
| 已尝试 / 计划 | 实際触发的调用与计划调用总数 |
| 收到响应对象 | 公共客户端正常返回了 `LLMResponse`，不等于业务通过 |
| JSON / 契约通过数 | 通过响应完整性检查后，继续通过相应校验的次数 |
| 任务成功数 | 响应完整、字段合法、与预期答案一致 |
| 状态分布 | 哪些失败最常发生，不把网络问题算成分类理解错误 |
| 调用耗时中位数和最大值 | 已尝试调用的客户端观测耗时；包括失败等待，另列成功调用中位数 |

如果 10 次计划调用全部尝试，2 次超时、2 次格式错误、6 次答对，端到端成功应为 `6/10`，不能只拿答对的 6 次作为分母。本脚本遇到连接问题会提前停止；此时只显示覆盖和计数，不给完整成功率，也不把未运行样本计作“模型答错”。

本节的三个通过计数都在响应完整性检查之后统计；截断或未知结束原因不再解析，所以不要将这里的“JSON 通过数”解读为所有原始文本的纯语法可解析数量。

生成速度与端到端延迟不同。Ollama 原始响应还可能提供加载和生成耗时，但当前 `LLMResponse` 没暴露这些字段；本脚本不会从客户端总耗时推导出服务端的纯生成速度。`None` token 计数会显示为未知，不能算成 0。[Ollama 计数和耗时字段](https://docs.ollama.com/api/chat)

初始能力报告还应记录硬件、量化、服务版本、冷启动/预热、内存或显存观察值；没有测量就写“未测”。本脚本只打印模型标识、参数、样本版本、调用结果、延迟和已知 token 数，未自动采集硬件、服务版本或内存峰值。使用远程付费服务时另记录实际费用，不根据 token 数猜测未确认的价格。

模型选择要在同一组条件下同时看任务成功、失败分布、延迟和运行资源。一次回复流畅、一次速度快，或极小样本的高分，都不足以证明某个模型更适合整个 Agent 项目。

退出码：离线故障实验全部匹配预期为 0，否则为 1；真实实验流程跑完且没有调用错误时为 0，但仍可能有分类错误；发生调用错误或网络中止为 1，用户中断为 130。进程退出成功不等于每个模型回答都正确。

## 9. 常见误区与练习

- 给所有异常加自动重试，掩盖请求错误或造成重复写入。
- 将 HTTP 200、正常返回、格式合法与任务成功混为一谈。
- 只统计解析成功的答案，删掉格式失败后计算“准确率”。
- 把 `unknown` 当作 `stop`，或者把字段齐全的截断 JSON 当作成功。
- 根据“不能回答”等关键词就自动断言模型触发了安全拒绝。
- 反复看保留集改 Prompt，然后用原保留集报告独立测试分数。
- 将 token 数当作内存占用，或只比较少量调用的平均耗时而不看失败等待和冷启动。

练习：

1. 对本节的 12 个故障场景，先预测状态，再运行；解释离线实验中的“通过”究竟验证了谁。
2. 手动模拟 6 次计划调用，在第 2 次连接失败后停止；说明剩余 4 条为何是未运行而不是分类失败。
3. 将 JSON 和字段都正确的投诉分类故意改成售后，指出哪一层发现问题。
4. 为开发集补充一条多意图消息和一条信息不足消息；先定标注规则，再运行模型。
5. 解释什么时候需要更换保留测试集，并设计一个与现有消息不同的业务场景。
6. 用开发集做一次真实基线；先看失败类型，再决定要改 Prompt、预算、客户端还是服务配置。

## 10. 本周复盘、验收与下一节

第二周三节串起来是：知道当前接口怎样工作 → 校验收到的数据 → 对失败和一批实验结果做可靠判断。

- [ ] 能区分模型、服务、客户端和评分器的问题，不只根据错误文本猜原因。
- [ ] 能说明空回答、截断、未知结束和文本拒答的不同。
- [ ] 能解释为什么本节不自动重试，尤其是写操作超时的风险。
- [ ] 能完成离线故障实验，并说明其不代表真实模型能力。
- [ ] 能分清开发集与保留集，保证预期答案不进入模型请求。
- [ ] 能用全部计划样本解释成功率分母，并对中断运行保留“未运行”状态。
- [ ] 能描述一份模型基线报告的已知信息与未测项目。
- [ ] 已完成一次真实模型基线，并结合原始结果复盘；未运行则保留待完成。

用户要求进入本节不代表上一节已经通过验收，历史待确认项继续保留。扩课后下一节进入[第 02 模块 Session 04：服务商适配、能力契约与流式组装](../session_04/README.md)，完成本模块新增课后再进入第三模块工具调用。教案已备好，明确推进时直接取用；本次批量备课不改变当前停留点。

<details>
<summary>计划 10 次，2 次超时、2 次格式错误、6 次答对，分母是什么？</summary>

全部 10 次已经尝试，端到端成功率是 6/10=60%。超时与格式错误都占用计划样本，不能删去后报告 6/6。若中途停止，则额外区分未运行覆盖率，不把未运行伪装成模型分类错误。

</details>

<details>
<summary>合法 JSON 但结束原因是 length，能算成功吗？</summary>

本课程不算。结束原因表明触发长度限制，即使当前文本碰巧形成正确对象，也不能当作正常完整回答。应明确记为 truncated，分析输出预算或请求设计，不能静默修补后通过。

</details>

<details>
<summary>本节其他练习的参考思路</summary>

离线故障只验证客户端/评分器处理；连接失败停止后的剩余样本记未运行；合法投诉被分成售后由任务层发现；新开发样本先固定标签再看输出；保留集一旦用于调参就不再独立；真实基线先按失败层定位问题，再决定改 Prompt、预算或服务。

</details>
